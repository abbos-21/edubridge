PART B — PRODUCT SUMMARY AND GOALS
=====================================================================

EduBridge is a trilingual (Uzbek Latin default / Russian / English) study-abroad
navigator for students from Uzbekistan: 5 countries (Malaysia, Hungary,
Germany, Turkiye, South Korea), 50 universities (10 per country in 3 groups:
3 highly selective, 4 balanced, 3 more accessible), 7 national grants (MTCP,
MIS, Turkiye Burslari, Stipendium Hungaricum, DAAD EPOS, GKS-U, GKS-G), an AI
advisor, a profile builder, application plans, calendar and budget.

WHY A BACKEND
The frontend-only design is a ceiling: no accounts, no cross-device sync, no
real admin, no reminders, no controlled AI cost, no data freshness automation.
v2 adds a backend so that:
G1. Students can sign in and keep profile, plans, documents and chats across
    devices, privately and deletably.
G2. The AI works everywhere (not only on claude.ai) through a secure,
    rate-limited, cost-controlled server proxy.
G3. The catalogue lives in a database with an admin interface, review
    workflow and audit trail, instead of Python dicts and manual builds.
G4. Facts stay fresh: automated monthly source checks produce a reviewed
    change list; nothing is published without human approval.
G5. Students get reminders (Telegram bot, calendar files) and can share a
    one-page summary.
G6. The product is safe to run on a public domain.

NON-GOALS (still out of scope)
- Admission or scholarship probabilities of any kind.
- Submitting applications on behalf of students; storing university portal
  passwords.
- Payments, native mobile app, countries beyond the five.

USERS / ROLES
- Guest: browses catalogue, uses demo profiles, rule-based tools. No account.
- Student: signed in; owns private data; uses AI within quota.
- Editor: can edit catalogue drafts and submit for review.
- Admin (owner): approves publication, manages users/roles, quotas, sees
  audit log and cost dashboard.

PART C — NON-NEGOTIABLE RULES (carry over from v1, must stay true)
=====================================================================

DATA HONESTY
C1. Every fact shown as official has a source URL and a check date. Anything
    not found stays empty and the UI says "not confirmed".
C2. Never invent IELTS, GPA, fees, deadlines, grant amounts or links.
    Aggregator websites are not sources.
C3. IELTS is used for matching only when ieltsScope = "general".
C4. A missing value is never shown as zero or "free".
C5. Past deadlines show as "closed" with their year; unverified dates never
    produce suggested task dates.
C6. Grant criteria are never shown as university entry requirements.
C7. Groups (tiers) are EduBridge guidance, not an official classification.
    QS 2027 values name the page they came from.
C8. NO admission or scholarship probability anywhere (UI, API, AI output).

AI HONESTY
C9. One advisor identity: honest criticism first; eligibility is never
    presented as likely selection.
C10. Official facts only from catalogue records passed in the prompt
     (ground() picks at most 20). The AI cannot browse and must say so.
C11. Links not in grounded records are flagged "unverified" (checkLinks).
     Quotes in analyses are verified against the student's text (quoteIn).
C12. Every structured AI reply is validated; a malformed reply is an error,
     never a fake analysis.
C13. Only minimalProfile() reaches the AI (no name, birth year, institution).
     Documents go to chat only when the student switches sharing on.
C14. Rewrites use [placeholders] for facts only the student knows; originals
     are never overwritten.

PRIVACY / SECURITY
C15. Never ask for or store university application passwords; the UI says so
     next to every apply link.
C16. Collect the minimum. Student can export and delete all their data.
C17. No secrets in frontend code. Admin tools only behind real server-side
     authorisation (the old client-side AdminGate is NOT sufficient).
C18. Respect websites' terms and robots.txt; do not bypass logins/CAPTCHAs.

PART F — BACKEND FUNCTIONAL REQUIREMENTS
=====================================================================

All endpoints under /api/v1, JSON, Zod-validated input and output, consistent
error shape {error:{code,message,details?}}, request id in every response.
Document with OpenAPI (fastify-swagger), served at /api/docs in non-prod only.

F1 — AUTH AND ACCOUNTS (replaces FR-17)
- POST /auth/telegram   verify Telegram Login Widget payload (HMAC with bot
  token, auth_date freshness <= 10 min), create/find user, set session cookie.
- GET  /auth/google/start, /auth/google/callback  (OIDC, state + PKCE).
- POST /auth/logout; GET /me; PATCH /me (lang, display name).
- Account linking: a signed-in user can link the second provider.
- Sessions: 30-day sliding expiry, revocable, list/revoke other sessions.
- No password storage anywhere. No email or phone collected unless Google
  provides email (store only if needed for account recovery; show it to the
  user).
- Guests keep working with localStorage exactly as today. On first sign-in the
  app offers "Upload local data to your account" (see F2).
Acceptance: forged Telegram payload rejected; expired payload rejected;
session cookie is httpOnly+Secure+SameSite; logout invalidates server-side;
account deletion removes the user and all rows (tested).

F2 — SYNC OF STUDENT DATA (replaces FR-17 sync)
- REST resources per table in Part E: GET/PUT/DELETE on /me/profile,
  /me/applications, /me/documents, /me/chats, /me/interviews, /me/growth,
  /me/budgets, /me/events, /me/saved, /me/settings.
- Optimistic concurrency: each record has `version` (or updated_at); PUT with
  stale version returns 409 with the server copy. Frontend merges or asks.
- POST /me/import-local  accepts the localStorage object (edubridge:v1),
  validates it, merges without overwriting newer server data, returns a
  report of what was imported/skipped.
- GET /me/export  returns everything as one JSON file (data portability).
- DELETE /me  deletes the account and all data immediately (hard delete),
  confirmed by re-auth or typed confirmation.
- Authorisation on EVERY record: queries are always scoped by session user id.
  A negative test suite must prove user A can never read/write/delete user
  B's records for every resource (Part K).
- Limits: per-user caps (e.g. 50 documents, 2 MB per document text) with
  clear errors.
Acceptance: data created on device 1 appears on device 2 after sign-in;
user isolation test passes for all resources; delete removes everything.

F3 — AI PROXY (replaces server/index.mjs)
- POST /ai/chat (streaming via SSE), POST /ai/json (structured), POST
  /ai/ocr (images, size-limited) — thin, task-typed endpoints. The backend
  owns prompts' task selection, tier choice and the grounding step:
  * Move prompts.ts, schemas.ts, context.ts into packages/shared (or
    apps/api) so the SAME prompt and validator code runs server-side.
  * The server builds grounded context from the DB catalogue (ground(),
    max 20 records), applies minimalProfile(), calls Anthropic, validates the
    reply with the Zod/validator, runs checkLinks and quoteIn, and returns
    result + flags. A malformed reply returns 502 ai_bad_reply, never fake
    data.
- Auth required for AI (guests get rule-based fallback only).
- Rate limits and quotas: per-user per-minute burst limit; daily and monthly
  token/request quotas by role (configurable in DB/env); 429 with Retry-After
  and a plain message key for aiErrorText().
- Abuse protection: max request size, max prompt chars, timeout (e.g. 90 s),
  abort support when the client disconnects, one in-flight request per user
  per action.
- Cost control: log every call in ai_usage; admin cost dashboard (F8); global
  daily budget cap in env that disables AI with a clear message when reached.
- Caching: identical grounded Q&A within a short TTL may be cached; never
  cache user documents' analyses across users.
- Privacy: do not log prompt bodies or document text (log sizes only).
  Retention for ai_usage metadata: 12 months.
- Keep GET /ai/health (is a key configured, is AI enabled, remaining quota
  for the caller).
Acceptance: frontend AI features all work through the proxy with no API key in
the browser; quota exceeded returns 429 and the UI shows the plain message;
tests prove that prompts carry the honesty rules and validators reject bad
replies (port the existing advisor tests to run against the server code).

- GET /catalog/universities?country=&tier=&level=&q=&subject=&language=&

- The web app switches from the bundled catalog.json to this API, but KEEPS a

Acceptance: all catalogue pages render from the API; with the API down, the

F5 — DOCUMENT HANDLING

F6 — REMINDERS AND CALENDAR (replaces FR-20)

PART H — SECURITY REQUIREMENTS
=====================================================================
H1. HTTPS everywhere (Caddy), HSTS, secure headers (CSP without unsafe-inline
    where feasible, X-Content-Type-Options, Referrer-Policy, frame-ancestors
    'none').
H2. CORS: allow only the app origin. Cookies httpOnly/Secure/SameSite=Lax;
    CSRF token or double-submit for state-changing requests.
H3. Input validation with Zod on every route; reject unknown fields; size
    limits; no raw SQL (Prisma only; if raw SQL is needed, parameterised).
H4. Authorisation: central policy functions; every query scoped by user id;
    role checks for admin routes; deny by default.
H5. Rate limiting per IP and per user (auth endpoints stricter); lockout/
    backoff on repeated auth failures.
H6. Secrets in env only; rotate-able; startup fails fast if required secrets
    are missing; never logged. Telegram bot token and Anthropic key only on
    the server/worker.
H7. Logs contain request ids, user ids and metadata, never document text,
    prompts, tokens or cookies.
H8. Dependencies: lockfile, `npm audit` in CI, Dependabot/Renovate config.
H9. Backups: nightly pg_dump to off-server storage, 14-day retention,
    documented restore procedure tested once; encrypted at rest.
H10. Data protection: privacy page updated (what is stored, why, retention,
     deletion). Account deletion hard-deletes within 24 h including backups'
     natural rotation (document it). Honour export requests via /me/export.
H11. SSRF protection for the recheck fetcher (block private IP ranges,
     limit redirects, only http/https).
H12. Admin actions require a re-authenticated recent session and are all
     written to audit_log.
